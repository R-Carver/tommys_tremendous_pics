Project Decisions

tommys_pics: portfolio website for a starting professional photographer.

This file is the single record of project decisions. Update it whenever a decision is made, changed or reversed. Do not delete old decisions; mark them as superseded.

Constraints

  • A first version must be ready to demonstrate within 1–2 hours of implementation.
  • Hosting is on Cloudflare, free plan. No custom domain is needed at the start.
  • A very simple CMS (content management system) is mandatory. An admin must be able to upload images, set their category and set their order.
  • The CMS security must be very simple and quick to implement.
  • Expected volume: 20–100 images at the start, in 4–6 categories.

Decisions

D-001

Base template: HTML5 UP "Lens"

Accepted2026-10-19
Decision
We use HTML5 UP Lens as the base of the public website.
Why
It is built only for photos. It has a thumbnail strip and a full-screen viewer with smooth crossfades. It is plain static HTML, CSS and JS with no extra complexity.
Alternatives
HTML5 UP Multiverse, HTML5 UP Big Picture, and hosted builders such as Pixpa (look only, no reusable code).
Notes
The license is Creative Commons Attribution. The site must credit HTML5 UP, for example with a footer link. Lens has no categories, so we add a category menu ourselves. Style ideas to borrow later: color fading in on hover (Brother Jones, Pedro Agostinho Cruz).
D-002

Hosting: Cloudflare Pages (free plan)

Superseded by D-0142026-10-19
Decision
The site is hosted on Cloudflare Pages under the free *.pages.dev address.
Why
It is free, fast, and can run small server functions next to the static site.
Notes
A custom domain can be added later without changing the code.
Update
2026-10-19: replaced by Workers with static assets (D-014). Still Cloudflare, still free, address becomes *.workers.dev.
D-003

Architecture: static site + Pages Functions + custom mini CMS (Option B)

Accepted2026-10-19
Decision
The public site is static. It loads the image list at runtime from an API. A small admin page and a few Pages Functions handle upload, ordering and deletion. No framework and no build step.
Why
Changes appear immediately without a rebuild. No external accounts are needed. The code is small (about 200–300 lines) and fully under our control.
Update
2026-10-19: the backend runs as a Worker with static assets instead of Pages Functions (D-014). The architecture is otherwise unchanged.
Alternatives
Option A: images in the Git repository and a Git-based CMS (Decap CMS or Sveltia CMS). Rejected because every change needs a rebuild, the admin needs a GitHub account, and the OAuth login setup is too slow for the time budget.
D-004

Image storage: Cloudflare R2

Accepted2026-10-19
Decision
Images and the manifest are stored in an R2 bucket named tommys-pics-images (binding BUCKET). Images are served by the Worker at /img/<path>.
Why
R2 is real file storage with path-like names. The free tier gives 10 GB of storage and free downloads. 100 photos use about 1% of that.
Fallback
Cloudflare may require a payment method to activate R2. If that is not acceptable, we switch to Workers KV (1 GB, 25 MB per entry, 1,000 writes per day on the free plan). The code changes little.
D-005

Data model: one manifest file, category prefixes

Accepted2026-10-19
Decision
A single manifest.json in R2 is the source of truth for categories, images and order. The order of an array is the display order. Image files use the category as a path prefix.
Why
Changing the order only rewrites one small file. Files never need to be renamed.
Example
landscape/a7f3-full.jpg
landscape/a7f3-thumb.jpg
manifest.json

{
  "categories": [
    { "id": "landscape", "title": "Landscape" },
    { "id": "portrait",  "title": "Portrait" }
  ],
  "images": {
    "landscape": [ { "id": "a7f3", "title": "Fog over the lake" } ],
    "portrait":  []
  }
}
D-006

Image processing in the browser

Accepted2026-10-19
Decision
The admin page resizes each image in the browser before upload. It creates a large version (about 2400 px wide) and a thumbnail (about 600 px wide).
Why
Cloudflare's image resizing is not part of the free plan. Resizing in the browser needs no server-side processing.
D-007

CMS security: HTTP Basic Authentication

Accepted2026-10-19
Decision
A middleware function protects /admin and /api/admin/* with HTTP Basic Authentication. The password is stored as the Cloudflare secret ADMIN_PASSWORD, never in the code.
Why
It takes about 10 minutes to build and needs no login page.
Limits
There is no protection against password guessing, so the password must be long. There is no real logout.
Later
We can switch to Cloudflare Access (email one-time code login, free up to 50 users) without changing the site.
D-008

Ordering UI: up/down buttons first

Accepted2026-10-19
Decision
The first admin version uses "up" and "down" buttons to reorder images. Drag and drop may follow later.
Why
It is faster to build and fits the time budget.
D-009

Deployment with Wrangler

Accepted2026-10-19
Decision
We create Cloudflare resources and deploy with the wrangler command-line tool. Since D-014 the deploy command is wrangler deploy (config: wrangler.jsonc).
D-010

Frontend/backend boundary: GET /api/gallery

Accepted2026-10-19
Decision
The public frontend depends only on GET /api/gallery. The response contains categories, images and complete image URLs. The full contract is in docs/api-contract.md.
Why
The frontend must not know where images are stored or how they got there. Then the frontend can be built and tested before the backend exists, and the tests stay valid when the real backend replaces the mock.
Rules
The frontend treats image URLs as opaque strings and never builds storage paths. Array order is display order. Unknown fields are ignored. The stored manifest.json (D-005) is a backend detail; /api/gallery is a view of it.
D-011

Categories: mixed into one list for now

Provisional2026-10-19
Decision
The first draft shows all images in one list. Categories are interleaved round-robin (one image from each category in turn), and the order inside each category is kept. The setting CATEGORY_MODE in gallery.js also supports 'grouped'.
Why
It is not yet decided whether visitors should see categories at all. The API and data model keep categories, so a category menu can be added later without backend changes.
Open
Show a category menu or not. If yes: filter in place, or one page per category.
D-012

Local development with a mock API

Accepted2026-10-19
Decision
Stage 1 (now): frontend/mock/mock-server.mjs serves public/, /api/gallery and /img/* from generated mock data. frontend/mock/prepare-mock-data.mjs builds that data from local-images/<category>/ with the same sizes the admin page will produce. Stage 2 (now done, see D-016): wrangler dev runs the real backend locally with a simulated R2 bucket (Miniflare).
Why
Everything must be testable locally. The mock can simulate situations on demand (?scenario=empty|error|slow|broken|single), which the real backend cannot easily do.
Notes
The mock server uses port 8788, so it can run next to wrangler dev (port 8787). The scenario is read from the page URL via the Referer header, so the frontend code contains no test logic.
D-013

Template adjustments

Accepted2026-10-19
Decision
  • Lens files are kept original where possible. Project styles go in assets/css/custom.css.
  • main.js is loaded by gallery.js after the thumbnails exist, because Lens reads them only once at start.
  • One patch in main.js (marked [tommys_pics]): the viewer also continues when an image fails to load. Without it, one missing image locks the whole viewer.
  • The viewer shows the whole photo (contain) instead of cropping it (cover).
  • Thumbnails are square and slightly muted; they turn to full color on hover and when active.
Verified
Tested in headless Chromium at 1440×900 and 390×844 with all mock scenarios: thumbnails render, viewer and keyboard navigation work, empty/error messages show, a broken image no longer blocks navigation.
D-014

Workers with static assets instead of Pages

Accepted2026-10-19
Decision
The site runs as one Cloudflare Worker with static assets. wrangler.jsonc points the static files to frontend/public and the Worker code to backend/src/index.js. The paths /api/* and /img/* always go to the Worker (run_worker_first). Everything else is served as a static file.
Why
Pages Functions must live in a folder named functions/ at the project root, next to the static files. That blocks a clean frontend/backend split. With Workers, both locations are free to choose. Workers with static assets is also the setup Cloudflare currently recommends for new projects. Static file requests are free and do not count against the Worker limit (100,000 requests per day on the free plan).
Later
For the admin page (step 2), /admin* is added to run_worker_first, so the Worker can check the password before the admin page is served.
Alternatives
Keep Pages (D-002) with functions/ at the root. Rejected because of the folder constraint.
D-015

Repository structure: frontend and backend separated

Accepted2026-10-19
Decision
frontend/public/   static site, deployed as-is (no build step)
frontend/mock/     mock API server + mock data builder (frontend dev only)
backend/src/       Worker: routing, /api/gallery, /img/*, manifest handling
backend/scripts/   seed-local.mjs: fills the LOCAL simulated R2 bucket
tools/             dev tooling shared by both (image resizing)
tests/             Playwright smoke tests (frontend + backend API)
docs/              decisions, API contract
wrangler.jsonc     deployment config that joins frontend and backend
Rules
The frontend never imports backend code. The only connection is the HTTP contract (D-010). Code in tools/ is never deployed.
D-016

Local backend: wrangler dev with simulated R2

Accepted2026-10-19
Decision
npm run seed fills a local simulated R2 bucket (stored in .wrangler/) from local-images/. It uses Wrangler's getPlatformProxy(), which always works locally and never touches the real bucket. npm run dev runs the Worker on port 8787 with the same bucket. No Cloudflare account is needed for local work.
Verified
The frontend works against the real backend without any change, which confirms the boundary from D-010.
D-017

Backend security rules for image delivery

Accepted2026-10-19
Decision
/img/ only serves keys of the form <category>/<id>-full.jpg or -thumb.jpg. Everything else returns 404, including manifest.json and paths with ...
Caching
Images: public, max-age=31536000, immutable plus ETag, and repeat requests return 304. Gallery: no-cache.
Concurrency
Only one admin edits at a time. If two saves of the manifest overlap, the last one wins. This is accepted for now.
D-018

Automated smoke tests with Playwright

Accepted2026-10-19
Decision
tests/frontend.spec.mjs checks the gallery only through the API contract, so it must pass against the mock and against the real backend. tests/backend.spec.mjs checks the API itself (contract, image headers, 304, blocked paths). Error scenarios run only against the mock. Each test runs on a desktop and a mobile viewport.
Commands
npm run dev + npm run test:e2e (real backend), npm run mock + npm run test:e2e:mock (mock). One-time setup: npx playwright install chromium.
Result
2026-10-19: real backend 15 passed, mock 12 passed, and 45 of 45 passed in three repeated runs (no random failures).

Open questions

  • Photographer name, bio text and contact details.
  • Final list of categories (4–6), and whether visitors see categories at all (D-011).
  • The Lens CSS loads the Roboto font from Google Fonts. For a site run from Germany this is a GDPR (General Data Protection Regulation) risk; we should host the font ourselves before going live.
  • Placeholder texts in index.html (name "Tommy", tagline, Instagram link, email).
  • Does activating R2 require a payment method on this Cloudflare account? If yes, is that acceptable? (See D-004.)
  • Where to place the HTML5 UP attribution.
